## Standards 轴：规范、架构与解耦

### S1 · 高危 · 审核状态与任务创建不原子（静态可证）

[`TaskReviewService.confirm`](../../../../../wn-server/app/src/main/java/com/wannian/server/app/task/TaskReviewService.java) 先将待审单 `PENDING→CONFIRMED`（第 94–98 行），再 `prepare`、提交带 `TaskDraft` 的 Turn（第 99–120 行）。仅正常返回失败时回退；提交抛异常、进程退出或结果不确定时会留下 `CONFIRMED` 且可能没有 Task，卡片不再列入待确认列表。也存在提交实际成功后错误回退、再次确认造成双任务的反向风险。违背周期计划“审核确认后经同一提交落库”的不变量。

**修复：**审核占用与 Turn/Task 提交建立同事务方案，或使用持久 `CLAIMED` 中间态、稳定幂等键和启动对账。对账先查询 Task/Turn 是否已提交，再决定完成确认或恢复 PENDING。补异常、进程退出、重复点击及重启测试。**通过条件：**每张审核卡最多建一个 Task；确认失败可恢复，且不存在永久 `CONFIRMED` 无任务。

### S2 · 高危 · 任务终态与交付意图不原子（静态可证）

[`DefaultTaskRuntime.acceptResult`](../../../../../wn-server/app/src/main/java/com/wannian/server/app/task/DefaultTaskRuntime.java) 在第 398、436 行先提交任务终态，随后调用 `notifyDelivery`。该钩失败两次后只记日志并放弃（第 458–501 行）。进程在提交与钩之间退出，或钩持续失败时，任务已结束但没有 durable 交付意图，无法依赖后续重试恢复。违反架构文档的事务/outbox 原则。

**修复：**在任务终态同一事务写入待交付事件或 outbox；通知/Busy/Idle 分流由独立 worker 幂等消费。为既有终态行增加对账，按 `taskId + runId/开火次数 + 终态` 去重。**通过条件：**在提交前后故障注入及重启后，任务和交付记录一致，用户最终只见一次结果。

### S3 · 高危 · Busy 提醒在失败回合后滞留（live 实测）

[`DurableTurnScheduler` 的完成钩](../../../../../wn-server/app/src/main/java/com/wannian/server/app/stream/DurableTurnScheduler.java) 仅在第 817–823 行成功完成时调用 `flushAfterTurnCompleted`，失败/取消钩没有同等处理。2026-09-29 live 回合 `5c898002-8336-45d1-9354-168921e535e5` 返回 `MODEL_TIMEOUT`；提醒已在消息中心，但任务 `470c3ec1-a08a-4a82-b0fc-694575e29c98` 的 Busy 交付 `a1419190-bc68-4d80-b4b9-f71d31fec922` 仍为 `QUEUED`，会话没有提醒气泡。

**修复：**失败/取消后按会话状态安全冲刷或转 Idle；启动和周期对账孤儿 Busy 队列。保留现有消息写入与状态 CAS 同事务去重。**通过条件：**成功、失败、取消和重启四种路径均不会留下永久 QUEUED；通知与会话消息按规格各出现一次。

### S4 · 高危 · TaskRuntime 识别具体执行器，替换 seam 会漏结果（静态可证）

[`DefaultTaskRuntime.dispatchNext`](../../../../../wn-server/app/src/main/java/com/wannian/server/app/task/DefaultTaskRuntime.java) 第 304–307 行以 `instanceof LocalTaskExecutor` 读取私有结果缓存并调用 `acceptResult`；[`TaskExecutor`](../../../../../wn-server/kernel/src/main/java/com/wannian/server/kernel/task/TaskExecutor.java) 接口只有 `dispatch/cancel`。替换成测试或远端执行器时，`Accepted` 后没有通用结果回报通道，Run 会依赖租约过期收口。与架构文档明确的 `TaskRuntime→TaskExecutor` seam 不符。

**修复：**同步接口返回带结果的封闭类型，或定义异步结果回报端口；Runtime 只依赖接口。补 Manual/Fake/Remote 风格执行器的契约测试。**通过条件：**不同执行器都能完成、失败、取消并持久提交结果，无具体类判断。

### S5 · 中风险 · 通知中心复合操作没有共同原子边界（并发风险）

[`NoticeCenter`](../../../../../wn-server/app/src/main/java/com/wannian/server/app/notice/NoticeCenter.java) 第 269–299 行对 `CopyOnWriteArrayList` 做遍历、定位、替换与裁剪；后台发布和 HTTP 撤销可并发。单次集合操作线程安全并不能保证整段原子，同一任务可能重复入列或出现索引竞态。

**修复：**统一锁保护发布、撤销、批量清理、裁剪，或用不可变快照 CAS；补并发发布/撤销测试。**通过条件：**同 task/kind/终态最多一条，线程交错不抛异常。进程内有界通知本身是 2.5.10 已批准设计，不列为缺陷。

## 同工作区混入的阻断性回归

这些改动相对 0.2.4 基线存在，但不属于 2.5 Task 设计本身。由于它们会随同一次交付进入产品，必须在 2.5 归档前处理。

1. **P0：记忆衰减数值被改坏，有批量墓碑风险。** [`MemoryDecay`](../../../../../wn-server/kernel/src/main/java/com/wannian/server/kernel/memory/MemoryDecay.java) 将衰减底数 `0.5` 改为 `2.5`（第 43、75 行），并把 `IMPORTANCE_EPHEMERAL` 从 `0.35` 改成 `2.35`（第 30 行）。重要性先钳到 `[0,1]`，故第 80 行条件对所有超过 14 天的记忆恒真；会把原本不应清理的高重要性记忆判作墓碑。四个记忆相关测试已失败。应立即恢复原参数和半衰期公式，检查是否已有误墓碑数据，并跑记忆全套回归；不要只改测试期望。
2. **P1：工具策略新锁定项没有更新契约测试。** [`ToolUsePolicy`](../../../../../wn-server/kernel/src/main/java/com/wannian/server/kernel/tool/ToolUsePolicy.java) 第 28–37 行新增锁定 `propose_background_task`，而 [`ToolUsePolicyTest`](../../../../../wn-server/kernel/src/test/java/com/wannian/server/kernel/tool/ToolUsePolicyTest.java) 第 66–95 行仍断言旧清单，造成两项失败。先确认产品决议确实要求它不可关闭，再更新测试与管理页可见性契约；若不要求锁定，则改策略。不能仅删除断言。
3. **P1：历史迁移脚本被改动，旧库升级可能校验失败。** 已交付的 [`V001`](../../../../../wn-server/app/src/main/resources/db/migration/V001__initial.sql) 与 [`V008`](../../../../../wn-server/app/src/main/resources/db/migration/V008__memory_relationship.sql) 的注释相对 HEAD 被修改。Flyway 校验历史脚本校验和；应保持已发布迁移字节不变，把文档路径更新放到新文档，使用旧版本数据库副本做升级验证。
4. **P2：其他数值疑似同类替换。** [`PersonaTextScanner`](../../../../../wn-server/app/src/main/java/com/wannian/server/app/persona/importer/PersonaTextScanner.java) 第 100 行将重叠阈值从 `0.35` 改成 `2.35`，而重叠率最大为 1，去重判断永不成立；模型默认 `presencePenalty` 也从 `0.35` 变成 `2.35`（[`ModelSamplingSettings`](../../../../../wn-server/app/src/main/java/com/wannian/server/app/model/ModelSamplingSettings.java) 及配置文件）。逐项与原设计核对，恢复无依据的数值替换并做对应测试。
5. **P2：超时后页面没有持久失败提示。** [`recoverActiveTurns`](../../../../../wn-server/app/src/main/resources/META-INF/resources/chat/app.js) 第 343–357 行跳过历史 `FAILED` Turn。本次长回复流式文字在超时后刷新即消失，只留下用户句；应显示“回复超时”及重试入口。不要在未调查模型耗时与流式状态前简单提高 120 秒硬截止。

## 修复顺序与复验门槛

1. **先阻断数据回归与升级风险：**恢复记忆/重叠/采样参数，保持 V001/V008 原样；核对现有数据库是否已有错误墓碑，跑旧库升级与记忆测试。
2. **再修 Task 持久化边界：**S1 审核原子性、S2 终态与交付意图原子性；对崩溃点做故障注入和启动对账验证。
3. **修交付与执行器协议：**S3 失败/取消 Busy 队列恢复，S4 通用 TaskExecutor 回报；再处理 S5 并发通知。
4. **补 UI 与规格：**失败 Turn 提示；澄清工具锁定清单；将 L7 改为负向隔离验收。L1 默认 30 分钟可用独立实时时长测试留证。
5. **最终门槛：**全量 Maven 测试通过；新增审核/交付/执行器的故障注入与并发测试；真实服务重测提醒成功、超时、取消、重启四条路径；核对所有待交付表无孤儿行。届时再决定 2.5.13 是否归档。

两轴统计：Standards 5 项（最重为 S1/S2/S3/S4）；Spec 2 项（最重为 Busy 失败交付与审核确认恢复）。另有同工作区阻断性回归 5 组，其中记忆墓碑风险最高。
